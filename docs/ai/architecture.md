# Prism architecture (for agents working on Prism)

Read this before changing anything structural.

## Process model

Electron, three sides, one typed contract.

- `src/shared/types.ts` is the domain model. `src/shared/ipc.ts` is the IPC contract: channel names in `CH`, the `PrismApi` interface that preload exposes as `window.prism`.
- `src/main/` runs Node with full privileges. `Services` (services.ts) owns the settings store, vault, SQLite repo, terminals, MCP clients, the current `Workspace`, and the `AgentHost`. `ipc.ts` is only handlers; logic lives in `src/core`.
- `src/renderer/` never touches the network, the filesystem or secrets. It talks to `window.prism` (see `lib/ipc.ts`) and keeps UI state in zustand stores under `state/`.
- `src/core/` is plain Node code with no Electron imports so it can be tested headlessly.

## Packaging

`scripts/package.mjs` builds the Windows installer with electron-builder, but stages the app by hand in `<temp>/prism-build/<version>/stage` (all build work happens under the temp folder; only the finished installers are copied to `dist/` or `--out`, so no runnable Prism.exe is left where Windows search finds it; the unpacked app for smoke tests is `<temp>/prism-build/<version>/out/win-unpacked`): `out/` plus two real modules, node-pty (prebuilt binaries, unpacked from the asar) and typescript (the compiler file and its `lib.*.d.ts`), and the ripgrep binary under `resources/bin`. Everything else is bundled by electron-vite (zod and the Claude Agent SDK's JavaScript are excluded from externalisation for that reason). The staged folder is electron-builder's whole project and declares `packageManager: traversal`, so it never tries to ask pnpm for a dependency list. If main ever needs another package at run time, either bundle it or add it to the staging step; it will not be picked up by itself. `build/installer.nsh` adds the shortcuts page to the NSIS wizard. On Linux the same script builds an AppImage and a tar.gz: node-pty has no Linux prebuild, so it stages `node-pty/build/Release/*.node` compiled by `pnpm rebuild:pty` (prebuilds win when they exist). Build it in WSL from a clone in the Linux filesystem (a clone of the main repo, `-b work`: the worktree's .git points at a Windows path). WSL needs libnss3, libnspr4 and libasound2t64 to *run* it; without sudo, `apt-get download` + `dpkg -x` into a folder and `LD_LIBRARY_PATH` works for testing. WSL stops the distro between separate `wsl.exe` calls, so start and test in one session.

## The agent loop

`core/agent/engine.ts` → `runTurn()`:

1. Persist the user item, build tools (`core/agent/tools`), build the system prompt (`prompt.ts`: environment, git summary, project instruction files PRISM.md / AGENTS.md / CLAUDE.md).
2. Rebuild provider messages from the persisted transcript (`context.ts: messagesFromItems`). Everything the model saw is in the `items` table, including tool calls and results, so the agent remembers across turns and app restarts.
3. If the estimated context passes `settings.agent.compactAt × contextWindow`, `compactSession()` summarises everything before the last user turn into one `system/compaction` item.
4. Call the provider with streaming (`core/providers/*`). Stall and transient failures retry up to three times with backoff; the UI gets a `status` and a repeated `step-start` so it resets its live buffers.
5. Persist the assistant item, then run tool calls: permission decision (`permissions.ts`), approval round-trip through `AgentHost`, execute, persist the tool item. Read-only tools run in parallel when `settings.agent.parallelTools` is on.
6. Loop until the model stops calling tools, hits `maxSteps`, errors, or is aborted.

Events (`AgentEvent`) are published per root session on `agent:event:<sessionId>`. Sub-agents run `runTurn` recursively (depth 1 only) on a child session and tag their events with `agent`.

## Claude Agent (Claude Code as the engine)

A session whose model has `endpointId === 'claude-agent'` does not go through `runTurn`. `AgentHost.send` routes it to `core/claude/runner.ts: runClaudeTurn()`, which starts the Claude Code program installed on the machine through `@anthropic-ai/claude-agent-sdk` (`query()` with a streaming input that stays open for the turn) and translates its message stream into the same `AgentEvent`s and transcript items. The renderer does not know the difference.

- `locate.ts` finds the executable (Settings path → `~/.local/bin` → PATH → the VS Code extension's copy). Prism never ships its own; the SDK's JavaScript is bundled into main, its 240 MB native binary is not used. `claudeEnv()` strips a parent Claude Code session's markers.
- `catalog.ts` asks the CLI for `supportedModels()`, `accountInfo()` and `supportedCommands()` without sending a message, caches the answer in `userData/claude-agent.json` for a day, and turns it into virtual `ModelInfo`s (`Services.listModels()` appends them). There is no endpoint row: `Services.resolveModel()` returns null for these refs, so use `Services.usable(ref)` when the question is "can a session run on this". The e-mail address from `accountInfo()` is deliberately not stored.
- `translate.ts` renames Claude Code's tools and arguments to Prism's (`Edit {file_path}` → `edit_file {path}`, `Bash` → `shell`, `mcp__prism__x` → `x`) so rows, diff cards, approval cards and automation hooks are shared. The transcript copy is for display and for other models; the real conversation is Claude Code's session file.
- Prompt caching: everything before the conversation must be identical on every turn, or Anthropic re-stores the whole conversation (a 500k-token write instead of a read). So `AgentHost.claudeFixed()` (Prism intro, tool note, copy note) is the only `append` to the system prompt, and `claudeContext()` (skills, session instructions, rules, pinned files) goes into the user message as a notice, only when its sha1 differs from `ClaudeSessionState.given`; never before a slash command (it must come first); again after a compact_boundary or a rewind (`given` is cleared); a short "no longer applies" when it becomes empty. Measured: a pin added between two Haiku turns read 28,366 cached tokens and wrote 647; before, the same change re-stored everything. Never put anything that changes (a time, a count, file contents) in `claudeFixed`.
- One CLI process per turn, resumed with `resume: <claude session id>`. The id and the rewind bookkeeping live in `SessionExtras.claude` (`ClaudeSessionState`). Rewind (`AgentHost.rewound`) sets `resumeAt` so the next turn passes `resumeSessionAt`. If the session file is gone the turn restarts once without `resume`, with the transcript as a text digest; the same digest covers turns another model answered in between (`synced`).
- Assistant messages arrive one content block at a time with the same API message id; `flush()` joins them into one `AssistantItem` at `message_stop`. Usage comes from the stream events. Cost is recorded only when the CLI runs on an API key (`apiKeySource !== 'none'`).
- `canUseTool` is the approval round trip: `AskUserQuestion` → question cards (answers go back in `updatedInput.answers`), `ExitPlanMode` → the plan panel (approve returns a `setMode` permission update; the turn continues, so `Run.external` stops `AgentHost.plan` from queuing a follow-up turn), everything else → an approval card ("always" returns the CLI's own `suggestions`). Mode changes mid-turn go through `Query.setPermissionMode` (`Run.claude.setMode`); `allowDangerouslySkipPermissions` is always set so Full auto can be switched on live.
- SDK hooks: `PreToolUse` runs Prism's before-tool automations and snapshots a file before `Edit`/`Write` (that is where diffs and checkpoints come from; files outside the workspace are neither diffed nor checkpointed), `PostToolUse` runs after-tool/after-edit automations.
- `bridge.ts` offers Prism's own tools (gadget_*, check_project, show) as an in-process MCP server named `prism`. It answers the handful of MCP messages by hand so the tools keep their JSON Schemas; the full `ToolResult` (meta, diff) is picked up again in `finishTool` via `bridge.take()`. These tools follow Prism's risk rules, not Claude Code's.
- Messages with `parent_tool_use_id` belong to a Claude Code sub-agent: they are emitted with an `agent` tag and, like Prism's own sub-agents, not stored in the parent transcript.
- Bringing in a conversation Claude Code had elsewhere: `conversations.ts`. `listClaudeConversations()` scans `~/.claude/projects/*/*.jsonl` (or `CLAUDE_CONFIG_DIR`), reading only the first and last 256 KB of each file (cwd, first ask, latest `ai-title`). `readClaudeConversation()` streams the file line by line: assistant lines sharing a `message.id` join into one item, `tool_use` goes through `toPrismCall`, `tool_result` becomes a `ToolItem` cut to 4000 chars (pictures only counted), compact summaries become `compaction` items, user lines count only when `origin.kind` is human (or absent and not Claude Code bookkeeping), and messages typed mid-turn are `attachment` lines of type `queued_command`. Sidechain (sub-agent) lines are skipped. The session gets `SessionExtras.claude = {sessionId, lastUuid, synced: last item}` so the next turn resumes with no digest. Claude Code finds a session by the folder it runs in (`projects/<path with every non-alphanumeric char as ->`), so `placeForResume()` copies the file there unless a newer copy is already there. `Repo.appendItems` inserts in one transaction (a 145 MB conversation came in as 6,000 items in under a second).
Tool servers in a Claude session come from two places that do not know about each other: Claude Code's own `~/.claude.json` (and a project `.mcp.json`), and Prism's `settings.mcp`. The second used to reach only Prism's own engine, so an agent asked to add a server would run `claude mcp add` — and a running Claude session rewrites `~/.claude.json` from the copy it read at startup, so the entry appeared and then vanished. `AgentHost.mcpForClaude()` now passes Prism's enabled servers straight into the SDK's `mcpServers` option (secrets fetched from the vault at that moment), which no file write can undo. `claudeOwnServers()` reads the names already in Claude's config so they are not offered twice; the name a server's tools get is its Prism name lowercased with runs of punctuation turned into dashes. The list is rebuilt for every message, so a server added in Settings reaches the next message without restarting the session.
- Anthropic's terms: third-party products may not offer claude.ai login to their users without approval. Prism only drives the user's own installed CLI; do not add a login flow, and keep the name "Claude Agent" (not "Claude Code") for the feature.

## Tools

Each tool implements `AgentTool` (`tools/types.ts`): a JSON-schema spec, `risk()` (null = never needs approval), `summary()` for the UI, `readOnly`, and `execute()`. Filesystem tools are jailed to the workspace (`core/fs/paths.ts: jail`). Mutating file tools call `ctx.checkpoint()` first so a turn can be rewound. The shell tool streams output through `ctx.output()` and supports background jobs. MCP tools are bridged as `mcp__<server>__<tool>`. The user's own tools and `use_skill` are described under "Custom tools" and "Skills".

## Background work, notices and wake-ups

`core/agent/background.ts` defines `BackgroundHost` (implemented by `main/background-host.ts`, created by `AgentHost`) and the tools that need no engine: `wake_me`, `list_waiting`, `cancel_wakeup`, `list_sessions`, `message_session`, `watch_job`, plus the helper tools `message_agent`, `stop_agent`, `merge_agent_work`, `run_team` (lead agent only; `buildTools` options `background`, `helpers`).

News reaches an agent as a `SystemItem` with subkind `'notice'` (`meta.source`: job, watch, timer, helper, team, session, session-reply, lead; `meta.wake`). `context.ts` sends it to the model as a user message prefixed "[Notice from Prism, not written by the user]". Delivery (`Background.notify`): a session the engine is running a loop for (`enter`/`leave`, called by `runTurn`) gets it in its inbox; `runTurn` drains the inbox at the top of every step, and when the model gives a final answer while news is waiting (`pending`) it loops once more instead of finishing. An idle lead session: notices arriving within 400 ms are gathered, then `handIn` starts a turn through `AgentHost.send(..., automatic=true, notices)`; `runTurn` then opens the turn with those notices instead of a user item (`RunInput.notices`). It is written into the transcript instead when the wake limit (`settings.agent.wakeLimit`, counted in `wakes`, reset by `userSpoke` on any user send) is reached or the session's project is not open. `turnEnded` (from `send`'s finally) hands in news that came too late for the turn and sends replies other sessions asked for (`replyTo`). Every hand-in also sends `CH.Notice` for a desktop notification / toast.

Jobs: `shell` background jobs carry an `owner` (`ToolContext.background`) and notify it on exit unless `notify:false`, killed (job_kill, the header ×) or the turn was stopped. Watchers live on the job (`feedWatchers` splits lines, groups hits for 1.5 s). Timers are stored in session extras (`wakeups`), checked every 15 s by a ticker that only runs while some session has one (`repo.sessionsWithWakeups`); repeats use `parseEvery` from automations. `getSessionExtras` validates fields one by one: new extras keys must be added there or they are dropped on the next save.

Helpers (`core/agent/helpers.ts`): every `spawn_agent` creates a `HelperRecord` in the lead's extras (`helpers`) with its own child session, so `message_agent` can either drop a notice into a running helper's inbox or run another `runTurn` on its session (it keeps its whole conversation). Running helpers are tracked in a module map (`runningHelpers`, `stopHelper`). Background helpers are not tied to the lead's abort signal; foreground ones are. An isolated helper gets a worktree from `copies.make`, which carries the project's uncommitted changes and untracked files over and commits them as the helper's starting point (`base`); `copies.apply` turns `git diff base` into a patch applied to the project (plain `git apply`, then `--3way` with the index reset). Approvals from a helper whose lead is idle go to `AgentHost.idleRuns` (`runOf`); a lead turn that ends with a helper's request still open moves it there, and the renderer keeps approvals that have an `agent`. The lead's turn reset keeps helper cards whose status is running.

UI: `panels/agent/Background.tsx` (`NoticeCard`, `BackgroundBar`), fed by the `background` agent event (`BackgroundState`) and `agent:background` on session select; `agent:background-cancel` stops a job, timer or helper.

## Settings added in 0.15

Most hard-coded behaviour now reads `Settings` (defaults in `core/store/settings.ts`, merged into saved files one level deep, so new keys appear for existing users): `agent.shellTimeoutSec` (shell tool via `ShellConfig.timeoutSec`), `agent.retries` (engine retry loop; delays reuse the last entry of `RETRY_DELAYS`), `agent.hookFixes`, `agent.maxTeam` (`HelperControl.maxTeam`), `agent.autoTitle`, `agent.sendKey` (Composer), `editor.*` (one `editorOptions()` in EditorPanel feeds both create and updateOptions; auto-save lives there too and saves quietly, so it never triggers next-edit suggestions), `editor.nextEdit`, `terminal.*` (makeTerminal + the settings effect; `fontFamily` empty follows the theme; `followProject` gates `Terminals.retarget`), `assist.*` (learn, specChecks, pagePictures in agent-host; catchUpAfterMin in CatchUp; agentMap in ExplorerView, replacing a localStorage flag; notifications in sessions.ts `notify`), `files.hidden` (`setHiddenDirs` in core/fs/paths.ts, applied by Services at start and on change; `isIgnoredDir` and ripgrep's `-g !**/name/**` follow it; the explorer only greys them out). `settings:defaults` returns `DEFAULT_SETTINGS` for "start over" buttons.

Bundled fonts are listed once in `renderer/lib/fonts.ts` (`fontOptions`, `fontReady`). Fixedsys Excelsior is a woff in `renderer/assets/fonts` declared in `styles/fonts.css`. Monaco and xterm measure glyphs once, so both wait for `fontReady` and then remeasure (`monaco.editor.remeasureFonts`, `term.clearTextureAtlas` + fit).

The shell tool's timeout and Stop kill the whole process tree on Windows (`taskkill /t /f`); `child.kill()` only stopped PowerShell and the command ran on.

## Memory

`core/memory/memory.ts`: `MemoryStore` keeps one markdown file per memory (front matter `name`, `description`) in `.prism/memory` (project, written through the Workspace so it works in WSL/SSH folders) and `userData/memory` (personal). `memoryIndex` is added to the lead's system prompt (`PromptInput.memories`). Tools: `memory_save` (create/replace; moving scope removes the old copy), `memory_read` ("*" lists), `memory_delete`. Settings, Agent lists them via `memory:list`/`memory:remove`. `remember` (PRISM.md notes) is unchanged.

## PDFs and notebooks

`core/agent/tools/documents.ts`: `read_file` sends `.pdf` to `readPdf` (unpdf, bundled: it is in the externalize exclude list; 20 pages at a time, `pages` picks) and `.ipynb` to `renderNotebook` (numbered cells, outputs, up to 4 output pictures). `edit_notebook` edits one cell and writes Jupyter's own layout (one-space indent, source as a list of lines); a replaced code cell loses its outputs.

## Sessions in their own copy

`sessions.extras.worktree` marks a session that works in a git worktree (`<userData>/worktrees/<project>-<id>`, branch `prism/<id>`, `core/git/worktree.ts`). `AgentHost.workspaceFor(sessionId)` is the single place that decides which folder a session's tools see; `deps(sessionId)`, checkpoint restore and the context report all go through it. Never call `requireWorkspace()` for something a session does. The renderer keeps `useSessions().copies`; for those sessions `onAgentEdit` does not open or flash editors, because the editor shows the project's files, not the copy's. Merging is plain `git merge --no-ff` in the project, so conflicts land in the normal resolver.

## Git

`core/git/git.ts` has status/stage/commit; `core/git/more.ts` has branches, remotes, stash, the commit graph, blame and conflicts. Everything in `more.ts` reaches the renderer through one channel, `git:op` (`name, ...args`), mapped in `main/ipc.ts` and typed on `PrismApi.git`: adding an operation means a function in `more.ts`, a line in `GIT_OPS`, a name in the preload list and a signature in `shared/ipc.ts`. Lane layout for the graph is done in the renderer (`panels/git/HistoryPanel.tsx: layout`). Conflict files are parsed, never merged by Prism: `parseConflicts` splits on git's markers and `resolveConflict` writes the chosen text and stages the file.

## Automations

`core/automations/automations.ts` (`AutomationManager`, one per app, re-reads `.prism/automations.json` when the workspace or the file changes). Hooks are called from two places: `executeCall` in the engine (`deps.hooks.before/after`, only for tools with a risk, i.e. not for plain reads) and `AgentHost.send`'s `finally` (`turnEnd`, with the files the turn wrote, collected from `file-touched` events in `emit`). A failing turn-end hook returns a follow-up that the host sends as an automatic turn, capped by `autoFixes` (reset by any user message). Watchers hang off the workspace's fs events and are muted while any agent run is active and for a few seconds after, so the agent's own edits cannot trigger them. Watchers and schedules each get a session titled `Automation: <name>` via `AgentHost.runAutomation`.

## Council (several models)

`core/agent/council.ts`. Other models never get the tool-calling transcript: `digest()` flattens it to text so any provider can read it. `opinion` stores its result as a `system/opinion` item, which `messagesFromItems` skips, so the lead model only sees it if the user sends it on. `compare` streams each model on `compare:event:<runId>` (key = `modelKey`); `adopt` appends the question and chosen answer as ordinary items. Routing: a session with `model: null` is "Auto"; `AgentHost.send` calls `routeModel` per message and does not persist the result, so the session stays on Auto.

## Session context

`sessions.extras` (JSON column, migration v3) holds a session's pinned files and extra instructions. `runTurn` reads them at the start of every top-level turn: `readPins` (`agent/contextReport.ts`, capped per file and in total) feeds `buildSystemPrompt({ pinned })`, and the instructions join `extra`. `contextReport` measures what would be sent right now, part by part, using the same prompt builder and tool list as the engine (`AgentHost.context`), so the panel cannot drift from reality. Dropping a tool result (`pruneItem`) rewrites the stored item to a one-line marker with `meta.pruned`. `remember` (tool and `notes:remember` IPC) appends under `## Notes` in `PRISM.md` via `appendNote`.

## Plan mode

`PermissionMode` has a fourth value, `plan`. A turn that starts in it gets read-only tools plus `present_plan` and `ask_user` (`buildTools({ plan: true })`) and a plan-mode section in the system prompt. `present_plan` blocks on `ctx.presentPlan()` (same round-trip shape as review). On approval it returns `meta.endTurn`, which makes the engine finish the turn after that tool, and `AgentHost.plan()` stores a follow-up that `send()`'s `finally` fires as the next turn in the mode the user chose: one visible line, the full plan as `expanded`. Feedback simply returns to the model; discard also ends the turn.

## Review

`shared/hunks.ts` splits a before→after change into hunks and applies a chosen subset (`applyHunks`); both sides use it. `propose_changes` (`tools/review.ts`) builds a change set in memory, calls `ctx.review()`, and writes only what comes back; the round trip mirrors ask_user (`review` / `review-resolved` events, `AgentHost.requestReview`, `agent:review` IPC), and a stopped run resolves it with nothing accepted. The same panel (`panels/review/ReviewPanel.tsx`) shows a finished turn's changes: "before" comes from the turn's checkpoint (`checkpoint:file`), "after" from disk, and undoing a hunk writes `applyHunks(before, after, all but that one)`.

## Problems and checkers

`core/checks/checks.ts` detects the project's own checkers from its files (plus `.prism/checks.json`), runs one on demand and parses the output into `Problem`s (`parseProblems` knows the tsc, eslint-unix, gcc-style `path:line:col`, Python traceback and JS stack-frame shapes; add a shape there, not in the UI). The same code backs the Problems panel (`checks:list` / `checks:run`) and the agent's `check_project` tool; the tool's results travel in `meta.results` and `state/sessions.ts` feeds them into `state/problems.ts`, so both sides always show the same list. Editor findings come from Monaco markers in the same store.

## Gadgets

A gadget is a folder (`<workspace>/.prism/gadgets/<id>` or `<userData>/gadgets/<id>`) with `gadget.json`, a UI (`index.html`) and an optional backend (`backend.mjs`). `core/gadgets/manager.ts` owns all of it.

- **UI**: a sandboxed iframe served from `prism-gadget://<id>/…` (own origin, no `allow-same-origin`). It talks to the host only by `postMessage`; `panels/gadget/GadgetPanel.tsx` is the bridge. The in-frame SDK and base CSS are served from `prism-gadget://_sdk/`.
- **Backend**: a separate child process (Electron as Node, `ELECTRON_RUN_AS_NODE=1`) running `core/gadgets/runtime.mjs` with the gadget's module. JSON lines over stdio: `init`, `tools/call`, `ui/call`, `shutdown` one way; `ui/emit`, `log`, `host/call` the other. It never runs in the main process.
- **Agent bridge**: backend `tools` appear to the agent as `gadget__<id>__<tool>`. Their specs are cached in `<userData>/gadget-cache/<id>.json` keyed by a fingerprint of the backend files, so the tool list is known without starting anything; a backend starts when one of its tools is first used. `agent/tools/gadgets.ts` adds the authoring tools (`gadget_sdk`, `gadget_write`, `gadget_read`, `gadget_look`, …). `gadget_look` captures the panel's rectangle with `webContents.capturePage`.
- **Lifecycle rules** (all in `manager.ts`): start/stop/reload of one gadget are serialised (`serial`), so two triggers can never start two backends. File changes go through `reconcile`: fingerprints of backend files vs UI files decide between a backend restart and a panel-only refresh. A backend stop kills its whole process tree; app quit does it synchronously (`disposeNow`).
- Changing data belongs in `api.dataDir` or `api.state`, never in the watched gadget folder.
- The text the agent reads before writing a gadget is `GADGET_SDK_DOC` in `core/gadgets/sdk.ts`. When the runtime API changes, change that text in the same commit.

## Remote workspaces (WSL and SSH)

The workspace root string says where the folder lives (`shared/place.ts`): a plain path is local, `\\wsl.localhost\<distro>\…` is WSL, `ssh://[user@]host[:port]/abs/path` is SSH. Two different mechanisms sit behind those:

- **Running things** (`core/remote/command.ts`). `command(cwd, argv)` and `shellCommand(cwd, line, …)` return the *local* process to spawn: the program itself, `wsl.exe -d D --cd P --exec …`, or `ssh … -- 'cd P && …'`. `git()`, the agent's shell tool, checks, automation hooks (`runLine`) and terminals all go through it, so they follow the folder without knowing. On the far side the shell is always a login bash; environment variables are passed with `env K=V`.
- **Files.** WSL needs nothing: Windows reads the UNC path, so `Workspace` works as is (ripgrep too). `fs.watch` cannot watch a UNC path, so `Workspace.poll()` compares sizes and times every few seconds, and `touched()` announces Prism's own writes at once. SSH has no local path at all: `core/remote/remoteWorkspace.ts: RemoteWorkspace` subclasses `Workspace` and does every operation as one `ssh host -- <script>` (GNU find/stat/cat/mv/rm; file bytes on stdin/stdout). One connection per operation: simple, no SSH library, 0.1–0.4 s each. A kept-open connection is the obvious next step if it feels slow.

Consequences to keep in mind: anything that takes a workspace path and then uses `node:fs` or spawns with `cwd` directly is local-only. For SSH that currently means project gadgets, checker detection, the TypeScript refactors, the scratchpad, worktree sessions and Claude Agent; each refuses with a plain message (`isRemote`/`placeOf` checks) rather than failing oddly. New code should use `Workspace` methods (`read`, `readRaw`, `list`, `kind`, `exists`…) and `command()`, never `ws.abs()` + fs. The `prism://workspace` protocol and the Browser's static server read through `readRaw` for SSH. Search over SSH runs `rg` there, falling back to `grep`/`find`. BatchMode means no password prompts; unknown host keys are accepted and remembered (`accept-new`), changed ones refused.

Tested against WSL Ubuntu and against a throwaway ssh2-based server on localhost running Git Bash; not yet against a real Linux server.

## Scratchpad

`core/scratch/manager.ts` keeps, per session name, up to two long-lived child processes: `runtime.mjs` (Electron run as Node, for JS and TS cells, spoken to over the process message channel) and `runtime.py` (replies are stdout lines starting with a marker, so stray prints still count as output). Both files are imported `?raw` and written into userData at start. The notebook panel uses the session `notebook`; each agent session gets `agent:<sessionId>`, ended after 20 idle minutes.

`transform.ts: prepareCell()` makes a JS/TS cell re-runnable in one process: TypeScript is transpiled (imports kept verbatim), top-level `const/let/function/class` and imports become plain assignments (the code runs through indirect eval in sloppy mode, so they land on the global object and outlive the cell), `import` goes through `__import`, which resolves relative paths against the project root and appends the file's mtime so edits are picked up, the final expression becomes the return value, and everything is wrapped in an async function on the first line so error line numbers match the cell. A line beginning with `(`, `[` or a backtick at the left margin gets a leading semicolon, because notebook cells end in `({…})` and JavaScript would otherwise read it as a call on the line above.

Outputs are `ScratchOutput` (text, stderr, error, json, table, html, image). HTML output is shown in an iframe sandboxed without scripts. Python is looked for in the project's `.venv`/`venv`, then on PATH, then in the usual Windows install folders (a per-user install is often not on PATH). The agent tool is `run_snippet` (`tools/scratch.ts`), risk medium like the shell.

## Browser preview

The Browser panel (`panels/browser/BrowserPanel.tsx`) shows pages in an Electron `<webview>` (`webviewTag: true`; `will-attach-webview` in `main/index.ts` strips any preload and forces a sandboxed, isolated guest in the `persist:preview` partition). On `dom-ready` the panel reports the guest's web-contents id to `main/preview.ts: PreviewManager`, which is how the main process, and through it the agent, reaches the page.

- **The dock must not detach the webview.** Re-attaching a `<webview>` destroys its guest and reloads the page. The panel is added with dockview's `renderer: 'always'`, and `DockController.open` skips `setActive()` for a panel already in front. `PreviewManager.front()` still re-reads the guest after focusing the panel, since the id can change.
- **Agent tools** (`core/agent/tools/browser.ts`, bridged to Claude sessions too): `browser_open` (an address, or a workspace file served by the static server), `browser_look` (JPEG of the page + visible text + console warnings/errors since the last look; the picture goes through the usual vision bridge), `browser_eval`. Eval wraps the script twice, as an expression then as statements: a script that fails to parse fails before anything runs, so the retry cannot repeat a side effect, and runtime errors are caught inside the page so their real message comes back (Electron's own rejection is opaque).
- **Static server**: `PreviewManager.serve()` serves the workspace on 127.0.0.1 with a random port, jailed through `Workspace.abs`. Auto-reload on file change defaults on only for pages from that origin.
- **Dev server**: detected from package.json scripts (dev, start, serve, preview, develop) and the lockfile's package manager; started in an ordinary user terminal titled "dev server", whose output is watched for a local address.
- **Handing things to the agent**: `useSessions.hand(sessionId, text, attachments)` puts text and pictures into a session's inbox, which the composer drains. The element picker is a script injected into the page that resolves with the clicked element.
- A production build started with `PRISM_DEBUG_PORT` exposes `window.__prism` like a dev build (`prism.debug`), which is how a built copy is driven for checks now that long dev-server sessions are not available.

## Asset viewers

`panels/preview/PreviewPanel.tsx` picks a viewer by file type: `ImageStudio` (CSS-transformed image for zoom/pan, an offscreen canvas for the pixel inspector and for the difference picture; compare sources are another workspace file or `git.blob(path)`, the file at HEAD as base64), `AudioStudio` (decodes with WebAudio for the waveform, plays from a blob URL so seeking always works), `Model3D` (react-three-fiber; `Bridge` hands renderer/scene/camera out of the canvas for the turntable and screenshots; the turntable draws the live canvas onto a 2D canvas per frame so tone mapping matches what is on screen, and encodes with gifenc). `fs.writeBinary` writes non-text files into the workspace.

The `prism://` protocol responses carry `Access-Control-Allow-Origin: *`: the renderer's origin is `file://` in a build, and without it a canvas that drew a workspace picture is "tainted" and its pixels cannot be read. Images that will be read back must be loaded with `crossOrigin = 'anonymous'`.

## Refactors

`core/refactor/refactor.ts` works out three project-wide changes and writes nothing: `renameSymbol`, `findReferences`, `moveFile` (the import edits that keep things working when a file or folder moves). For JS/TS it builds a TypeScript `LanguageService` per request over the nearest tsconfig/jsconfig inside the workspace (or every script in it), sharing one `DocumentRegistry` so parsed files are reused; file versions are mtimes, so it reads what is on disk (the renderer saves dirty editors first). Paths handed to the service must use forward slashes. Other languages fall back to whole-word ripgrep matches and the result carries `byMeaning: false`. Results are `RefactorPlan` (a `ReviewFile[]` change set, a note, and an optional `then` move to perform after the accepted edits are written, because the edits are computed against the old location).

Three entry points share it: the editor/explorer (`state/refactor.ts` → `refactor:*` IPC → `RefactorPanel` for preview, apply and one-level undo; `ReferencesPanel` for uses), Prism's agent tools (`tools/refactor.ts`: `find_references`, `rename_symbol`; `move_path` calls `moveWithImports`), and Claude sessions through the `prism` MCP bridge. `rename_symbol` has no approval card: in a mode where edits would ask, it sends the change set through `ctx.review()` instead, which is why `ToolContext` now has `mode()`. `typescript` is a run-time dependency (external, staged into the installer with its `lib.*.d.ts` files).

## Themes

A `Theme` (`shared/theme.ts`) is 33 colours plus a "look" (fonts, corner and border scale, glow, glass, blur, backdrop style, optional picture, label style). Built-ins are in `shared/themePresets.ts` (shared, so the agent's `set_theme` tool in the main process can build and check themes too; `shared/color.ts` holds the colour maths). `PRISM_PRESETS` are seeds (kind, backdrop, two accents) run through `buildColors()`, plus hand overrides; the six "classic" ones keep the original Prism surfaces exactly and carry the ids of the old accent setting, which is how a pre-theme `appearance.accent` still resolves. `EDITOR_PRESETS` (VS Code, GitHub, community themes) and `AI_PRESETS` use `exact()`: every colour by hand from the original palettes. `PRESETS` is all of them; `PRESET_GROUPS` lays out the gallery and `PRESET_HINTS` gives the "like …" line under a card. The user's own themes are stored whole in `settings.appearance.themes`; `appearance.theme` is the active id and `appearance.bg` is its backdrop so the main process can open the window in that colour.

`theme/apply.ts: applyTheme()` is the only place a theme reaches the screen. It writes CSS variables inline on `<html>` (overriding the defaults in `styles/tokens.css`), sets `data-kind`, `data-ambience`, `data-labels`, and calls the `onTheme` listeners: Monaco redefines its `prism` theme (`editorTheme()`), every live xterm gets `terminalTheme()` and has its glyph cache cleared. Chat code blocks use shiki's css-variables theme, so they recolour without re-highlighting. Gadget iframes are re-sent the variables by a MutationObserver on `<html>`.

`applyTheme` also sets `--fx` (glow strength, 0 for flat themes), `--accent-grad` and `data-fx` ("off" when a theme has neither glow nor glass). `styles/polish.css` is the finishing layer (drifting ambience, grain, lit panel edges, tab underline, composer ring while running via `.composer.working`, menu/dialog/toast entrances, cards lit under the pointer via `lib/spotlight.ts` setting `--mx/--my`); every decorative rule is gated on `:root[data-fx='on']` or scaled by `--fx`, so flat themes stay faithful. Changing to a different theme id runs inside `document.startViewTransition` and grows a circle from the last pointerdown; a repeat call for the same id while a switch waits for its frame is folded into it (`waiting`), otherwise the old snapshot would already show the new theme.

Line boxes in the conversation must land on whole pixels. The conversation's font sizes are fractional (`--c-fs` is 12.5px when compact, with 11.5px and 10.5px for the small text), so a multiplier line-height produces heights like 18.75px or 18.63px; rows then sit at half-pixel offsets, and as a turn streams in, everything above it shifts by fractions and the text re-rasterises a pixel out, which reads as shimmer while the agent works. `--c-lh` is therefore a px value per spacing (21/19/25), `polish.css` uses `var(--c-lh)` rather than its own multiplier for `.msg-assistant` and `.msg-user`, and the small-text classes have explicit px line-heights at the end of `agent.css`. Any new rule in the transcript should do the same. Test: with the agent running, every block inside `.transcript` should have an integer `getBoundingClientRect().height`, in every layout and spacing.

Rules for stylesheets, so every theme (including light ones) keeps working: never write a literal white or black overlay, use `rgb(from var(--tint) r g b / a)` (tint is white on dark themes and a dark colour on light ones) and `var(--shade)` for shadows; text on an accent fill is `var(--on-accent)`; literal corner sizes are `calc(Npx * var(--round))`; small capital headings use `var(--label-case, uppercase)` and `var(--label-space, …)`. Because the variables are inline, an attribute selector in CSS cannot override them: anything derived (glow off, line strength) is computed in `applyTheme`.

`settings/ThemeStudio.tsx` is the editor. It keeps a draft, applies it at once and writes settings 350 ms later; editing a built-in forks it (`base` remembers the origin for "Start over"). `sanitize()` fills gaps and rejects bad values in stored or imported themes. Theme files (`ThemeFile`, and packs of them) embed the picture; pictures live in `userData/themes` and are served as `prism://theme/<file>`. Installed font names come from `main/fonts.ts` (PowerShell on Windows).

## File history (core/history)

Every change the agent makes to a file is a row in `file_versions` (DB v4): session, workspace, the user item of the turn, the tool call id, path, before and after (null = did not exist). Both engines report changes as `file-touched` events carrying `callId` (the engine wraps each call's `ctx.emit`; the Claude runner adds the tool_use id). `AgentHost.emit` feeds `HistoryRecorder`: the first change to a path in a turn takes its "before" from the turn's checkpoint, later ones from the previous row's "after"; one queue per session keeps rows in order (`settled()` waits for it).

Shell commands (both engines, not background jobs) take `snapshotProject()` first: in a git repository a tree from a temporary index copied from the real one (`git add -A`, or `-u` above 200 MB of untracked files), elsewhere sizes, times and small contents in memory. Afterwards `changes()` lists what differs with the old content; those are added to the turn's checkpoint (`ctx.keepBefore`) and reported as file-touched, so rewind, the time machine and undo by request cover commands.

`history.ts` reads it back: `timeline()` (tool items in order with their versions; versions without an item become their own steps), `stateAt(index)`, `lineOrigin(path, line)` (newest version whose diff added that line's text; skips trivial lines; the reason is the assistant text before the call), `undoRequestPlan()` (per file `git merge-file -p now afterTurn beforeTurn`, i.e. the turn's change reversed onto today's file, shown as a change set). `catchup.ts` and `portable.ts` (sessions as files, ids remapped on import) build on the same rows.

## Skills

`core/skills/skills.ts`. A skill is a Markdown file with a small header (`name`, `description`, `when`, `always`). Project skills are read through the `Workspace` from `.prism/skills/` (so they work in WSL and over SSH); personal ones from `userData/skills`; one built-in (`extending-prism`, which documents skills and tools for the model) is appended in code. A project skill wins a name clash.

Loading is the same for both engines: `pickSkills(all, inUse, text)` returns the skills already in the session (`SessionExtras.skills`, names only) plus those whose `when` words appear in the message as whole words or phrases, plus the `always` ones. New ones are written back to the session extras (sticky) and announced with an `info` system item (`meta.skills`). `skillsPrompt()` puts loaded bodies in full and the others as one line each; it goes into the system prompt (`PromptInput.skills`) or into Claude Code's appended prompt. `use_skill` (`tools/skills.ts`) returns a skill's body and marks it in use; it is only offered when some skill is not loaded. Helper agents (depth > 0) get the session's loaded skills and no `use_skill`. System items are never sent to the model, so the note costs nothing.

## Custom tools

`core/customTools/`. One TypeScript file per tool in `.prism/tools/` or `userData/tools`, ending in `export default defineTool({...})`. `manager.ts` transpiles each allowed file with `typescript` (CommonJS output, no type check) and sends the JavaScript to a helper process, `toolhost.mjs`, which is the bundled source written to `userData` and run by Electron-as-Node.

Isolation, in two layers (read the header of `toolhost.mjs` before changing either):

1. Each file runs in its own V8 context made with `vm.constants.DONT_CONTEXTIFY` and `codeGeneration: { strings: false }`. The context is bare: no `process`, `require`, `fetch`, timers. The rule that makes it hold is that **no object from the helper's own realm is ever given to tool code**: any host object leads to the host `Function` constructor and out (`defineTool.constructor('return process')()` worked in the first version). So the in-context side (`GUEST`, a string evaluated inside the context) builds `defineTool`, `console`, `setTimeout`, `URL` and the `prism` object itself, and talks to the host through one function it holds in a closure. Only JSON strings cross, both ways; errors thrown by the host side are swallowed inside `GUEST` so a host-realm error object never reaches a tool.
2. The helper is started with `--permission --allow-fs-read=<its own file>`: no file access, no child processes, no workers, no native add-ons, even for code that got out of layer 1. Node's permission model does not cover the network, and Node documents it as a guard rail rather than a defence against hostile code. Do not describe the pair as a security guarantee in UI copy.

A tool's requests arrive at `CustomToolManager.serve()` tagged with the call id; the manager looks up that call's `ToolContext`, so files resolve against the right session's workspace (a worktree copy included) and writes go through `ctx.checkpoint` and emit `file-touched`. `shell.run` and `net.fetch` are refused unless the loaded definition lists them in `uses` (checked here, not only in the context). A call that outlives two minutes, or whose turn is stopped, kills the helper; it is restarted on the next use.

Allow list: `userData/tools-allowed.json` maps a file (project root + path, or absolute path) to the SHA-256 of its source. A file whose hash is not there is not sent to the helper; `list()` reports it as `waiting: 'new' | 'changed'`. `extend:create` and `extend:write` (the settings page) record the hash as part of saving; `extend:allow` is the button. Nothing the agent can call records a hash. Without this the agent could write a tool with `uses: ['shell'], risk: 'none'` and get commands that never ask.

Tools reach the model through `buildTools({ custom })` (never replacing a built-in name; `extend:list` reports the clash) and, for Claude sessions, through the `prism` MCP bridge like the other Prism tools. `shared/extend.ts` holds the templates and `TOOL_TYPES`, the declarations written beside the tools as `prism-tools.d.ts` and added to Monaco as an extra lib.

The settings page is `settings/ExtendSection.tsx`; files are edited in a modal through `extend:read/write`, which only reach files directly inside the four skill and tool folders.

## Renderer

- `shell/Dock.tsx` hosts dockview. Panels are registered in `COMPONENTS`; everything else opens panels through `state/layout.ts` (`useLayout().openEditor/openPreview/openAgent/...`), never by touching dockview directly.

## Conventions

- Comments explain architecture and non-obvious decisions, never narrate what the code does.
- UI copy is plain English. No "token", "projection", "adapter" on screen.
- Keep the renderer free of Node APIs. If you need a new capability, add it to `shared/ipc.ts`, implement it in `core/` or `main/`, expose it in `preload/`.
- Everything persisted goes through `core/store/repo.ts` (SQLite) or `core/store/settings.ts` (JSON). Secrets only through `core/store/vault.ts`.

- What the user is looking at: `state/looking.ts` holds one `Look` per open editor (path, line range, selected text, timestamp). `EditorPanel` reports on `onDidChangeCursorSelection` and `onDidFocusEditorText`; it deliberately does **not** forget on unmount, because dockview unmounts a panel whenever another tab in its group comes forward, and forgetting there made the feature silently do nothing when the agent and the editor share a group. Freshness comes from `useEditor.docs` instead: the composer only offers looks whose file is still open, so closing a tab with text selected drops it at once (the bug in VS Code's version). The newest look wins. `lookKey` identifies one look so dismissing it does not also dismiss the next; `settings.agent.editorContext` chooses selection+file / selection / off. The composer appends `@path (lines a-b, what I have selected)` plus a fenced copy (capped at 400 lines / 16k chars), or `@path (the file I have open)` with no contents. `@path` is not expanded anywhere in main, so a file-only look really does cost only its name.

## A conversation that stays fast

A long conversation must cost no more per streamed word than a short one. An imported Claude Code conversation can be thousands of items (one here is 6,538 items / 15.7 MB, ~35,000 DOM nodes), and three things conspired to make every token re-do all of it, which locked the window up for as long as the agent worked:

- `buildSegments` returns fresh objects, so every turn re-rendered. It now hands back the **same** `Segment` object for any turn whose contents are unchanged (`keepUnchanged`, compared by item identity; `steps` are wrappers so they compare by what they hold), and `Turn` is wrapped in `memo`. Both are needed: either alone does nothing.
- Everything passed to `Turn` must keep its identity. `useConv` was returning a new object every render; `renderItem`, `onOpenFile` and `onSendOpinion` were new functions every render. They are `useMemo`/`useCallback` now, and `renderItem` reads the transcript through a ref so it does not change when items do.
- `useStickToBottom` watched `{childList, subtree, characterData}` and, on every mutation, re-observed every child and set `scrollTop = scrollHeight` — a forced reflow of the whole document, several times per streamed character. It now folds everything into one pass per animation frame and re-observes children only when the child list really changed.

Measured on that conversation: one streamed word went from ~280 ms to ~33 ms, the same as a ten-item conversation. If you add a prop to `Turn`, make sure it is stable, or you put the freeze back. `content-visibility: auto` on `.turn` is a further ~2x and was deliberately left out: with the per-turn fix the cost is already flat, and estimated off-screen sizes risk reintroducing scroll jitter.
Typing had the same disease from a different direction: the message box grew itself by setting `height: auto` and reading `scrollHeight` on every keystroke, and that read forces the whole document to lay out again — about 35 ms a letter on a 6,500-item conversation against 0.5 ms on a short one. Chromium sizes the box natively now (`field-sizing: content`), so the measurement is gone and a keystroke costs ~0.3 ms; the old measuring path is kept behind `CSS.supports('field-sizing', 'content')`. Beware anything that reads layout (`scrollHeight`, `getBoundingClientRect`, `offsetTop`) in a handler that fires per keystroke or per streamed token.

## Phone app (remote clients)

The Android app is the same renderer as a window, talking to the computer's Prism over an encrypted WebSocket instead of IPC. Settings are hidden (`PHONE_APP` in SettingsPanel) until the APK ships.

- The page API is built by `shared/api.ts: makeApi(transport)`. The preload passes an IPC transport; the phone passes `remote/connection.ts: connect()`. `renderer/src/main.tsx` boots straight away when `window.prism` exists, else loads `remote/gate.tsx` (pair or connect), which sets `window.prism`, `window.__prismMobile` and imports `boot.tsx`. `App` renders `shell/MobileShell.tsx` (one full-screen page at a time, bottom tabs, menu sheet; it implements `DockController`, so `useLayout` works unchanged). `remote/assets.ts` swaps any `prism://` address on the page for a blob fetched through `host.asset`.
- `main/remote.ts: RemoteHost` (one per app, on `Shared`): identity key in the vault (`remote-identity`), paired devices in `userData/remote-devices.json`. Handshake text messages `pair` (proves the 10-minute code with an HMAC; Prism proves it back) or `hello` (known device), answered by `welcome` (with `addrs`, where it can be reached now; the phone puts these first in its saved list, keeping up to 8) or `refused`. Then every frame is sealed (`shared/remoteCrypto.ts`: X25519 static+ephemeral, HKDF-SHA256, ChaCha20-Poly1305 with a counter). A connected phone is a `Client` of kind `remote` on the front window's workbench; `WINDOW_ONLY` channels are refused. Connection handlers are wrapped (`guarded`) so nothing a phone sends can raise an error box; at most 16 connections may be mid-handshake at once.
- Reaching it: direct (`remote.port`, default 8793, `0.0.0.0`; `PRISM_REMOTE_HOST=127.0.0.1` for tests, which also avoids the firewall prompt), through a relay (`remote.relay`; frames in `shared/relayFrames.ts`; the relay only forwards sealed bytes), or through the router (`remote.upnp`).
The relay (`relay/server.js`, Node + `ws`, deployed on her VPS at `/opt/prism-relay`, systemd `prism-relay`, port 8794, Apache `conf-available/prism-relay.conf` proxying `/relay/` with `upgrade=websocket`): Prism holds one socket at `<relay>/host?id=&key=`, phones connect to `<relay>/client?id=`. The relay allocates a connection number per phone, tells Prism with a `RELAY_OPEN` frame, and from then on tags every frame with it; text stays text and sealed frames stay binary in both directions, so neither side can tell a relay from a direct connection. `RELAY_SECRET` is a path segment checked by the relay itself (wrong one = 404), which is why it needs no change in Prism: the whole `wss://host/relay/<secret>` string is just "the relay address". An id belongs to the first key that claims it (409 otherwise, which Prism reports as another Prism using that address); a dropped computer's slot is held five minutes so a reconnect keeps its id. It stores nothing and logs no payloads.
- `main/portmap.ts: PortMap` opens the port on the home router: SSDP search on every adapter plus the gateway directly, then the WANIPConnection/WANPPPConnection `AddPortMapping` (1-hour lease renewed every 30 min; 718 tries the next 4 ports; 725 retries as a permanent lease), else NAT-PMP to the gateway (from `route print` / `ip route`). An outside address in 10/8, 172.16/12, 192.168/16 or 100.64/10 (carrier-grade NAT) is reported as shared and the opening is closed again. `RemoteHost.dispose` closes it on quit (best effort). Test against stand-ins with `new PortMap(onChange, find, gw)`; on her own network the router answers neither UPnP nor NAT-PMP (Windows' own UPnP check agrees), so the real path has never opened a port.
- Mobile web build: `vite.mobile.config.ts` → `mobile/www` (gitignored; Capacitor's web folder). `src/renderer/mobile.html` has its own CSP allowing `ws:`/`wss:`.
- The `ws` package is bundled into main; its optional native helpers become empty stubs, so `WS_NO_BUFFER_UTIL`/`WS_NO_UTF_8_VALIDATE` are defined in `electron.vite.config.ts` (without them the first masked frame crashed the main process).
